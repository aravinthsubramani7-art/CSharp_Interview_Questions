JWT Authorization:
•	JWT – JSON Web Token
•	Let’s assume you are developing an Application like Facebook, as usual I am implemented Login Page with username and password, while we enter username and password and click login, the respective username and password will be sent to API Server (calling login endpoint). 
•	Now the Server will check with DB whether the given username and password are valid or not, if it is valid then we will send a success response to the client (Browser) and you successfully logged in.
•	After successful login, you are again calling the API Server for fetching the user detail against the user who logged in, and the server also fetches the information and while ready to send data, the server is doubting whether the valid user asking the detail or someone else.
•	Now Server asks us to prove we are valid user, so that we are again sends the username and password with the detail request, it again process the request and send data to client, now my user details are displayed in the browser screen
•	Now I am navigating to Friends page, again we are requesting the server to give friends list as same as above we are again sending the request with username and password
•	So, every request we are sending / proving we are a valid user, this type of authentication is called Basic Authentication.
•	But this is not a good approach, we are sending username and password on every request there is a high risk of password leak.
•	To overcome the problem, after successful verification of user credentials I am register the user with unique Session Id which is stored in Server and I will send the Session id to the browser
•	So that on every request we can only send session id alone with request, when we are sending request along with Session Id the server itself identify the user and are we a valid user, like this we are storing session in the server called Session Based Authentication.
•	Now we overcame the Problem faced in Basic Authentication, but in this Session Based Authentication also has a problem that, first of all we store the session id against the user is stored in Server only but what happens when there are more than 1 server, you may think why they have 2 server, because usually we have one server only but if the application is used by many of the people to handle the network traffic and fast response we will scale up the server so that now the application can handle the traffic efficiently, but the problem is when we have more than 1 server the API request goes randomly to any of the server
•	So the problem is when I login into the application, let’s assume the API request hit the Server1 and we are creating and storing and send the session id to browser, after you are request another then if it is goes to Server2 there we don’t have such session id then the server may think this is the hacker or someone else is misusing the browser.
•	Here the problem is the session detail are we are storing in server, but we can store the session in common DB and use in as much as server we want but every time hitting the DB is not a efficient way.
•	So we are planning to not store the session detail in the server, and now what we are doing is on the login itself the server is creating the long string and send it to browser, the long string is called token, so the server is instructing the browser to send this token in the header, every time we are requesting the API Call and the important thing is we don’t need to worry about which server is hitting the API call
•	With this token the server say we are valid user and identify the user from the token, to understand what is happening here we need to know how the token is created on login into the application
•	Once we are hit the login button the server verifies the username and password and after successful verification it will create a JSON of that user details such as user id, token expiry date, token created date, role and so on. But if is develop and requirement specific it may change based on the requirement and developer but we will not store the password or other sensitive data in it
•	Once the JSON is created, we will encode the JSON by using the Base64, this token is called JWT – JSON Web Token, once after encoded the token the server will sing the token with secrete key and that is called signature and every time we are requesting the API call we have to send this token in the header and server will first check the request has the token, if token is there then it will check the token is created by our server using that secrete key signature, once confirmed server will decode the token and extract the details
